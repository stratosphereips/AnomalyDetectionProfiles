How does the Zeek anomaly detector decide that traffic is unusual?

This page follows one record through the complete detector. It explains what is measured, how normal behavior is learned, how anomaly scores are calculated, and why a final alert is emitted.

1. The complete pipeline

The detector does not ask whether one packet matches a malicious signature. It asks whether the current behavior of an IP is sufficiently different from that IP's learned history.

1

Read

Parse the Zeek logs that are present. Missing TLS, SSH, or other logs do not stop the run.

2

Group

Place records into source-IP/protocol/time-window buckets and target-IP buckets.

3

Measure

Convert records into counts, ratios, novelty values, lexical signals, and transfer statistics.

4

Compare

Compare every current feature with its own adaptive historical model.

5

Decide

A feature becomes a reason when its z-score reaches the effective threshold.

6

Attribute

Select the exact Zeek records, UIDs, and FUIDs that best explain each reason.

7

Combine

Combine anomalous protocol and target components into one global IP score.

8

Adapt

Update the model quickly for small drift and slowly for suspicious behavior.

Key idea: feature definitions are fixed and understandable, but their normal values are learned separately for each IP and protocol. A high DNS count can be normal for a resolver and anomalous for a workstation.

2. Input logs and cross-log correlation

The input is a folder containing Zeek TSV or JSON logs. The detector uses every supported, IP-attributable log that exists, including conn, dns, http, files, ssh, ssl, dhcp, ntlm, smb_mapping, notice, and weird.

UID correlation

Zeek uses the same connection uid across logs. If C8abc appears in connection, HTTP, file, and weird records, the detector attaches that protocol context to the flows. The same responsible UID in multiple anomalous components is stronger evidence than unrelated events.

FUID correlation

HTTP fields such as resp_fuids can point to a files.log record. The detector enriches HTTP behavior with the exact linked file's byte count and MIME type. Shared FUIDs are reported as evidence but do not add ensemble score.

{
  "uid": "C8abc",
  "id.orig_h": "10.0.0.25",
  "id.resp_h": "203.0.113.8",
  "resp_fuids": ["F4xyz"],
  "uri": "/download/update.bin"
}
No TLS is required. If ssl.log is absent, only TLS-specific features and flow alerts disappear. DNS, connection, SSH, HTTP, file, target-IP, and global detection still work.

3. Records become time windows

Statistical detection needs repeated comparable observations. The detector therefore aggregates traffic into windows of window_seconds.

window_start = floor(Zeek timestamp / window_seconds) × window_seconds

With a 300-second window, timestamps 0–299 belong to the first window, 300–599 to the second, and so on. For source-side behavior, each model is keyed by:

(source IP, protocol, window)

A second detector view groups incoming behavior by target IP. This catches changes such as many sources or ports suddenly contacting one destination.

One hour

window_seconds = 3600
At most one observation per continuously active IP/protocol model.

Five minutes

window_seconds = 300
At most twelve observations during one hour.

Sparse traffic

Empty windows are not invented. A model advances only when that IP/protocol has records.

Smaller windows help short captures produce enough observations, but they also make each observation noisier. The baseline and analyzed traffic must use the same window size.

5. Learning normal behavior

Normal is learned independently for every feature of every IP/protocol model. During explicit training, the first training_hours observed windows are assumed benign. The name is retained for compatibility: it counts windows, not literal hours when the configured window is smaller than 3600 seconds.

Welford training

Welford's online algorithm updates the count, mean, and variance one observation at a time. It avoids storing the complete capture and is numerically stable.

count ← count + 1
delta ← value − old_mean
mean ← old_mean + delta / count
M2 ← M2 + delta × (value − new_mean)

Three ways to start

Benign prefix

training_hours > 0. The first N active windows of each model are fitted and cannot alert.

External baseline

normal_dirs. Trusted folders are fitted silently before the selected capture. They must contain the same IP identities to train those exact models.

Cold start

training_hours = 0. Early windows adapt the model, but statistical z-scores remain zero until minimum_points observations exist.

Zero training is not baseline-free detection. If minimum_points = 8, windows 1–8 seed the model and window 9 is the first statistically eligible window. Specialized TLS novelty can alert immediately in zero-training mode because it uses first-seen state rather than a statistical z-score.

6. How a feature becomes anomalous

Step A — compress heavy-tailed values

Counts and byte values can span several orders of magnitude. Every non-negative feature is compressed before modeling:

y = ln(1 + max(0, raw_feature_value))

This makes multiplicative changes easier to compare and prevents one enormous transfer from dominating the model.

Step B — measure distance from normal

When fewer than seven historical values are retained, the detector uses distance from the mean divided by the larger of standard deviation or the learned noise floor. With seven or more values, it uses the median and median absolute deviation (MAD), which are more resistant to outliers.

robust_std = max(1.4826 × MAD, minimum_noise_floor)
z = |current_transformed_value − historical_median| / robust_std

Step C — compare with the effective threshold

After at least ten benign training values, the detector can calibrate the threshold from the configured benign quantile. Otherwise, it uses the configured fallback threshold.

effective_threshold = learned_or_fallback_threshold / sensitivity
z < threshold
no anomaly reason
or
z ≥ threshold
feature becomes an anomaly reason

Try a transformed-space score

This calculator shows the exact robust comparison. Values are in transformed space, after ln(1+x).

Direction is explanatory, not a different formula. The detector reports whether the raw value is higher or lower than its learned mean. The z-score itself is absolute, so sufficiently unusual decreases can also alert.

7. Specialized detection techniques

Connection scan shape

Instead of declaring “more than N ports is always a scan,” the detector measures scan-like structure per window. Examples are port fan-out to one destination, failed connection states, scan-like Zeek history, short connections, and zero payload. Their values are then compared with that source's learned connection behavior.

DNS lexical and DGA-like behavior

The first DNS label is measured using length, Shannon entropy, unique-character ratio, vowel ratio, and digit ratio. A query is marked DGA-like when the first label is at least 8 characters, entropy is at least 2.8, unique-character ratio is at least 0.55, and either vowel ratio is at most 0.45 or digit ratio is at least 0.10.

DGA-like record → contributes to dga_like_count and dga_like_ratio → window value is statistically modeled

This predicate does not directly emit an alert. It creates explainable window features. mDNS on port 5353, .local, reverse lookups, and DNS service discovery are excluded from the DGA-like count.

TLS flow evidence

TLS additionally tracks state per source: known servers, JA3/JA3S fingerprints, and byte models for known servers. After training, a first-seen server or JA3S can create a flow alert. Unusual bytes to a known server require enough prior points for that server model. Flow alerts explain individual TLS behavior but do not vote directly in the global ensemble.

Exact cross-log evidence

UID and FUID correlation is deterministic, not statistical. It connects evidence known to belong to the same Zeek connection or file. Statistical models decide whether the associated window features are unusual; exact identifiers then strengthen and explain the relationship.

8. The baseline continues to adapt

Real networks change. After scoring a window, the detector updates the model with an exponentially weighted moving average (EWMA):

new_mean = old_mean + alpha × (current_value − old_mean)

Small deviation

Uses drift_alpha, normally 0.05. The baseline follows gradual legitimate changes.

Suspicious deviation

Uses suspicious_alpha, normally 0.005. The suspicious observation influences the model ten times more slowly, reducing baseline poisoning.

The current observation is always scored against the model that existed before that observation. Adaptation happens only after the decision.

9. From feature reasons to a global IP anomaly

Protocol score

Every feature whose z-score crosses its threshold becomes a reason. A protocol-window anomaly score is the sum of those reason z-scores:

protocol_score = Σ anomalous_feature_zscores
protocol_contribution = min(protocol_score, protocol_score_cap) / protocol_score_cap

The cap prevents a noisy high-volume protocol from dominating every other source of evidence.

Corroboration

Anomalous protocol windows and anomalous target-IP windows for the same IP and time window become independent components. Additional components receive a capped protocol corroboration bonus. Exact responsible UIDs shared across at least two anomalous components receive a second capped bonus.

global_score = min(1, Σ contributions + protocol_bonus + exact_UID_bonus)

A global event is emitted when the score reaches the sensitivity-adjusted global threshold, or when enough independent components agree.

Example: DNS contributes 0.30, HTTP contributes 0.30, and the second component adds 0.15. The global score is 0.75. If the responsible DNS and HTTP records share one exact UID, the default UID bonus adds 0.10, raising it to 0.85.

10. Why did the detector alert?

The detector stores reasons and responsible records rather than returning only a score. Attribution is feature-aware:

Reason typeHow responsible flows are selected
New peer or categorical valueRecords containing the first-seen peer or value.
Failure ratioRecords that satisfy the protocol's failure rule.
Port fan-outFlows to the destination with the largest set of ports.
DGA-like or no-answer ratioDNS records carrying the corresponding derived flag.
Numeric increase/decreaseRecords ranked in the anomalous direction by the relevant numeric detail.
Missing expected behaviorRepresentative records that were present; absent records cannot have a UID.

Each anomaly reports the feature value, learned mean, z-score, effective threshold, direction, explanation, responsible flow count, representative flows, and responsible UID/FUID sets.

11. Full example: a sudden DNS burst

Historical behavior

One workstation produced these DNS counts in seven active five-minute windows:

8, 9, 10, 10, 11, 12, 10

After ln(1+x), the historical median is approximately 2.398. MAD is approximately 0.087, so robust standard deviation is 1.4826 × 0.087 ≈ 0.129.

Current behavior

The workstation now produces 50 DNS records. Its transformed value is:

ln(1 + 50) ≈ 3.932

The robust z-score is approximately |3.932 − 2.398| / 0.129 = 11.89. This crosses a threshold of 3.5 and becomes a flow_count reason.

The same window may also show new peers, higher query entropy, more DGA-like queries, or more failures. Each crossing adds a separate reason and z-score. If HTTP or connection behavior is also anomalous for that IP, the global ensemble combines the independent evidence.
