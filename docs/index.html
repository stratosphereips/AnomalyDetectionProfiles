Summary

This overview answers four questions: Where does the data come from? What numerical values are produced? What becomes an anomaly? What is updated afterward?

One-sentence summary: Zeek records are correlated and grouped into time windows, aggregation rules calculate one current value for every monitored feature, each current feature value is compared with that feature's previous window values, threshold-crossing values become anomaly reasons, and corroborating component anomalies become a global IP anomaly before the models adapt.

Five stages of the process

Stage 1

Records and identity

Zeek produces protocol logs containing timestamps, endpoints, UID/FUID identifiers, and protocol fields. Missing TLS removes only TLS-specific detection.

Stage 2

Windows and features

Records from the same IP, protocol, and time interval are collected together and converted into numeric counts, ratios, novelty, lexical, transfer, and authentication features.

Stage 3

Statistical comparison

Each current feature value is converted with ln(1+x) and compared with previous values of that same feature using their median or mean, measured spread, noise floor, z-score, and threshold.

Stage 4

Reasons and adaptation

Only threshold-crossing features become reasons. Welford fitting handles trusted training; EWMA handles ordinary drift and slower strong-anomaly adaptation.

Stage 5

Outputs and evidence

Flow, protocol, target, and global outputs retain their scores, responsible records, UID/FUID evidence, and contribution details.

1. The complete pipeline

The detector does not ask whether one packet matches a malicious signature. It asks whether the current behavior of an IP is sufficiently different from that IP's learned history.

1

Read

Parse the Zeek logs that are present. Missing TLS, SSH, or other logs do not stop the run.

2

Group

For each time interval, collect records once by source IP and protocol, and independently by destination IP.

3

Measure

Convert records into counts, ratios, novelty values, lexical signals, and transfer statistics.

4

Compare

Compare every current feature with its own adaptive historical model.

5

Decide

A current feature value becomes a reason when its z-score reaches the effective threshold.

6

Attribute

Select the exact Zeek records, UIDs, and FUIDs that best explain each reason.

7

Combine

Combine anomalous source-IP/protocol components and the destination-IP component into one global IP score.

8

Adapt

Update the model quickly for small drift and slowly for suspicious behavior.

Key idea: feature definitions are fixed and understandable, but their normal values are learned separately for each IP and protocol. A high DNS count can be normal for a resolver and anomalous for a workstation.

2. Input logs and cross-log correlation

The input is a folder containing Zeek TSV or JSON logs. The detector uses every supported, IP-attributable log that exists, including conn, dns, http, files, ssh, ssl, dhcp, ntlm, smb_mapping, notice, and weird.

UID correlation

Zeek uses the same connection uid across logs. If C8abc appears in connection, HTTP, file, and weird records, the detector attaches that protocol context to the flows. The same responsible UID in multiple anomalous components is stronger evidence than unrelated events.

FUID correlation

HTTP fields such as resp_fuids can point to a files.log record. The detector enriches HTTP behavior with the exact linked file's byte count and MIME type. Shared FUIDs are reported as evidence but do not add ensemble score.

{
  "uid": "C8abc",
  "id.orig_h": "10.0.0.25",
  "id.resp_h": "203.0.113.8",
  "resp_fuids": ["F4xyz"],
  "uri": "/download/update.bin"
}
No TLS is required. If ssl.log is absent, only TLS-specific features and flow alerts disappear. DNS, connection, SSH, HTTP, file, destination-IP, and global detection still work.

3. Records become time windows

Statistical detection needs repeated comparable observations. The detector therefore divides time into intervals of window_seconds. In this guide, a window means the records collected for one identity during one such interval.

window_start = floor(Zeek timestamp / window_seconds) × window_seconds

With a 300-second window, timestamps 0–299 belong to the first interval, 300–599 to the second, and so on. The detector creates two different views of those records:

source-IP/protocol window = records with the same source IP, protocol, and window start
destination-IP window = records with the same destination IP and window start
These are two different views, not two names for the same thing. A source-IP/protocol window asks how one source behaved in one protocol. A destination-IP window asks what traffic one destination received across all supported protocols.

The two window views reuse the same eligible Zeek records, but apply different feature definitions and therefore calculate different feature values:

4. Feature extraction: what is measured?

Feature and feature value are different: a feature is a named measurement the detector tracks, together with its aggregation rule. During every active time window, Zeek records are aggregated according to that rule. The resulting number is the current feature value. This number enters the statistical computation; the feature definition itself does not.
feature definition: flow_count = count the matching records
records in current source-IP/DNS window = 47 DNS records
current feature value: flow_count = 47
statistical input: y = ln(1 + 47)

For every monitored feature, the detector calculates one value per active window and compares it with the values calculated for that same feature in previous windows. This sequence of previous values is the feature's history. Each feature has its own statistical model. Categorical fields can define features such as unique_* and new_* counts.

Every source-IP/protocol window applies the following feature definitions. Protocol-specific definitions are added afterward, so connection, DNS, and SSH windows do not calculate identical sets of feature values.

5. Learning normal behavior

training_windows defines one global interval at the beginning of the selected capture. Each unit means one configured aggregation window, so changing window_seconds also changes the training duration. The interval never restarts when a protocol first appears.

capture_start = timestamp of the first analyzed record
training_end = capture_start + training_windows × window_seconds
training traffic satisfies: capture_start ≤ record timestamp < training_end
Example: with training_windows = 6 and window_seconds = 600, training lasts 6 × 600 = 3600 seconds. If the capture starts at 09:00, only records from 09:00 up to but not including 10:00 are assumed benign. If SSH first appears at 11:00, it is already in detection: it does not receive its own six training windows.

Selected-capture windows are anchored at capture_start. Therefore the first N consecutive windows end exactly at training_end, and detection begins with window N+1. This prevents post-training records from entering a training value. Each feature model still learns independently, but all models share the same capture-wide training start and end.

Welford training

The detector needs more than an average. For every feature model it must learn both the normal center and the normal amount of variation. A current value three units above the mean may be highly unusual for a feature that normally changes by 0.2, but ordinary for one that normally changes by 10. Variance measures that normal variation and later becomes part of the z-score denominator.

What Welford produces

count records how many trusted window values were fitted. mean estimates their center. M2 accumulates their squared deviations, from which the detector obtains the sample variance.

Why calculate it this way?

A two-pass calculation must first collect the values and then scan them again. The simple one-pass expression mean(x²) − mean(x)² subtracts two potentially large, nearly equal numbers and can lose precision. Welford updates the same sample mean and variance in one stable pass as windows arrive.

For each trusted window, the detector first converts the raw feature value to value = ln(1 + raw_value). Welford then incorporates that transformed value with equal weight:

count_new = count_old + 1
delta = value − mean_old
mean_new = mean_old + delta / count_new
M2_new = M2_old + delta × (value − mean_new)
variance = M2_new / max(1, count_new − 1)
Why variance changes the decision: transformed histories [2.3, 2.4, 2.5] and [1.4, 2.4, 3.4] both have mean 2.4. Their standard deviations are approximately 0.1 and 1.0. A new value 2.7 is therefore about three standard deviations from the first stable history, but only 0.3 standard deviations from the second variable history. The mean alone cannot make this distinction.
Why it is needed here: the resulting mean and variance provide the initial statistical baseline for each feature of each source-IP/protocol model and destination-IP model. Welford does not itself declare anomalies; the later scoring step compares a new transformed value with the learned baseline.

Welford is used only for traffic explicitly trusted as training. Every trusted value deserves equal weight. After training, values are no longer assumed benign, so the detector switches to controlled EWMA adaptation: normal drift updates the model normally, while strong anomalies update it much more slowly. The implementation also retains training values separately for robust threshold calibration; Welford itself does not need to rescan them to update the mean and variance.

Three ways to start

Benign prefix

training_windows > 0. All and only records inside the first N aggregation-window units of the capture are eligible for trusted training and cannot alert.

External baseline

normal_dirs. Trusted folders are fitted silently before the selected capture. They must contain the same IP identities to train those exact models.

Cold start

training_windows = 0. Early windows adapt the model, but statistical z-scores remain zero until minimum_points observations exist.

A late protocol does not receive delayed training. A protocol or destination first seen after training_end starts with an empty model in detection mode. Its first minimum_points observations still produce statistical z-score zero and adapt through the ordinary cold-start EWMA path, but they are not labeled benign training and are not used for empirical threshold calibration.
Zero training is not baseline-free detection. If training_windows = 0 and minimum_points = 8, windows 1–8 seed a newly observed model and window 9 is the first statistically eligible window. Specialized TLS novelty can alert immediately because it uses first-seen state rather than a statistical z-score.

6. How the detector decides whether a feature value is anomalous

Step A — why transform every value with ln(1+x)?

ln is the natural logarithm. Network measurements such as connection counts and transferred bytes often have many ordinary small values and a few extremely large values. On the raw scale, an extreme value can pull the learned mean and variance strongly toward itself. The logarithm compresses the large end of the scale before the detector learns and compares values:

y = ln(1 + max(0, raw_feature_value))
Raw value xTransformed value ln(1+x)
00.000
10.693
102.398
1004.615
10006.909

Raw increases from 10 to 100 and from 100 to 1000 differ by 90 and 900, but both are tenfold increases. After transformation, their differences are approximately 2.217 and 2.294. The detector can therefore model relative change more consistently instead of treating high-volume features as though their absolute scale were the important part.

Why ln?

It converts a ratio into a difference: ln(1+b) − ln(1+a) = ln((1+b)/(1+a)). Distance in transformed space therefore reflects relative changes more than raw absolute differences.

Why add 1?

ln(0) is undefined. Using ln(1+x) keeps a raw zero valid and maps it to exactly zero.

Why max(0,x)?

All calculated feature values are intended to be non-negative. The maximum defensively prevents an unexpected negative value from entering the logarithm.

The logarithm does not remove an anomaly. It only changes the measurement scale. The current value and all historical values of that same feature are transformed identically, and the z-score is then calculated entirely in that transformed space.

Step B — measure distance from normal

When fewer than seven historical values are retained, the detector uses distance from the mean divided by the larger of standard deviation or the learned noise floor. With seven or more values, it uses the median and median absolute deviation (MAD), which are more resistant to outliers.

robust_std = max(1.4826 × MAD, minimum_noise_floor)
z = |current_transformed_value − historical_median| / robust_std

What is a z-score?

A z-score measures distance using the model's normal amount of variation as the unit. Subtracting the mean gives the ordinary distance from normal. Dividing by standard deviation answers: “How many standard deviations fit inside that distance?”

signed z-score = (current value − historical mean) / historical standard deviation
anomaly distance = |signed z-score|
Signed z-scoreMeaning
0The current value equals the historical mean.
+1The value is one standard deviation above the mean.
−2The value is two standard deviations below the mean.
|z| = 3.5The distance between the current value and the mean is 3.5 times the historical standard deviation, regardless of whether the value is higher or lower.

Example: if the mean is 100, standard deviation is 15, and the current value is 130, then z = (130 − 100) / 15 = 2. The value is two standard deviations above normal.

Once enough history exists, it substitutes the more outlier-resistant median and scaled MAD, and it also enforces the adaptive noise floor.

Noise floor: what it is and why it is needed

Simple definition: the noise floor is the smallest normal variation that the detector allows when calculating a z-score. It is a lower limit for the z-score denominator. Each feature model has its own noise floor.

A z-score divides the current distance from normal by the feature's usual variation:

z-score = distance from normal / normal variation

If previous values are identical, their measured variation is zero and division is impossible. If their variation is merely tiny, an insignificant change can produce an enormous z-score. The noise floor prevents both problems:

variation used by z-score = max(measured variation, noise floor)
z-score = distance from normal / variation used by z-score
Example: measured variation is 0.002 and the current distance is 0.03. Without a floor, z = 0.03 / 0.002 = 15. With a floor of 0.1, z = 0.03 / 0.1 = 0.3. The small change no longer looks like an extreme anomaly.

The noise floor is not an anomaly threshold and is not a minimum packet or byte count. It only prevents the model from claiming that normal variation is unrealistically close to zero. Its value is measured after the ln(1+x) transformation and starts at 0.1.

How the floor adapts

The appropriate minimum variation can differ between feature models. The detector therefore adjusts each floor from that model's recent residuals. A residual is the absolute difference between a transformed value and the model mean before learning that value:

residual = |current transformed value − old mean|

The latest 64 residuals are retained. Once at least five exist, the detector calculates a candidate and moves the current floor only 5% toward it:

candidate_floor = max(0.01, residual q10, 1.4826 × residual MAD)
new_noise_floor = 0.95 × old_noise_floor + 0.05 × candidate_floor

This gradual update lets the minimum follow recurring small model errors without jumping because of one observation.

Step C — compare with the effective threshold

After at least ten benign training values, the detector can calibrate the threshold from the configured benign quantile. Otherwise, it uses the configured fallback threshold.

effective_threshold = learned_or_fallback_threshold / sensitivity

7. Specialized detection techniques

Connection scan shape

Instead of declaring “more than N ports is always a scan,” the detector measures scan-like structure per window. Examples are port fan-out to one destination, failed connection states, scan-like Zeek history, short connections, and zero payload. Their values are then compared with that source's learned connection behavior.

DNS lexical and DGA-like behavior

The first DNS label is measured using length, Shannon entropy, unique-character ratio, vowel ratio, and digit ratio. A query is marked DGA-like when the first label is at least 8 characters, entropy is at least 2.8, unique-character ratio is at least 0.55, and either vowel ratio is at most 0.45 or digit ratio is at least 0.10.

DGA-like record → contributes to dga_like_count and dga_like_ratio → window value is statistically modeled

This predicate does not directly emit an alert. It creates explainable window features. mDNS on port 5353, .local, reverse lookups, and DNS service discovery are excluded from the DGA-like count.

TLS flow evidence

TLS additionally tracks state per source: known servers, JA3/JA3S fingerprints, and byte models for known servers. After training, a first-seen server or JA3S can create a flow alert. Unusual bytes to a known server require enough prior points for that server model. Flow alerts explain individual TLS behavior but do not vote directly in the global ensemble.

Exact cross-log evidence

UID and FUID correlation is deterministic, not statistical. It connects evidence known to belong to the same Zeek connection or file. Statistical models decide whether the associated window features are unusual; exact identifiers then strengthen and explain the relationship.

8. What is the model, and exactly when does it adapt?

The detection model is an online statistical model

This is not a supervised attack classifier and it is not trained with malware labels. It is an unsupervised, online statistical detector. Every feature has an independent AdaptiveStats model that stores and learns from its feature values for one source-IP/protocol pair or one destination IP. For example, the DNS flow_count values of 10.0.0.25 enter a different model from that IP's DNS failure_ratio values, and both are separate from every other IP.

Fixed feature logic

Code converts Zeek records into understandable values such as counts, ratios, entropy, bytes, new peers, and authentication attempts.

Learned statistics

Each feature model retains count, mean, variance, up to 256 recent transformed values, up to 64 residuals, a noise floor, and a threshold.

Statistical decision

The current feature value becomes unusual when its robust distance from the previous values of that same feature reaches the sensitivity-adjusted threshold.

Why this type of model? Network captures normally have no reliable labels saying “attack” or “benign,” and normal volume differs greatly between devices. Per-IP statistical models learn each device without labeled data, run incrementally with little memory, and produce a concrete feature value, baseline, z-score, and threshold that a human can audit. The trade-off is important: the model detects deviation from learned behavior, not malicious intent by itself.

Scoring a window and adapting the model are two separate decisions

After training, the detector scores each completed source-IP/protocol window and each completed destination-IP window. It calculates a z-score for every feature value in that window. A feature becomes an anomaly reason only when its z-score crosses its feature threshold. If none cross, the window is not anomalous. Only after this decision does the detector use the result to choose how quickly the model should adapt.

feature decision: z ≥ feature_threshold / sensitivity → add one reason
current window's anomaly score A = Σ z of reasons that crossed their thresholds
adaptation decision: A ≤ adaptation_score → drift update; otherwise → suspicious update
Do not confuse the thresholds. The feature threshold decides whether an anomaly reason exists. adaptation_score, normally 8, does not create an alert; it decides how quickly the completed window is learned. The global ensemble threshold is later still and does not control feature-model adaptation.

How training adaptation works: equal-weight Welford fitting

During trusted training, all fitted windows have equal weight. Welford is the baseline estimator described in the training section: it learns the center and variation without favoring recent training windows. If the old model contains n values, it adds the new transformed value y exactly:

n_new = n + 1
delta = y − mean_old
mean_new = mean_old + delta / n_new
M2_new = M2_old + delta × (y − mean_new)
variance_new = M2_new / max(1, n_new − 1)

This produces the ordinary sample mean and sample variance without recomputing them from the complete history after every window. Training values are retained separately for empirical threshold calibration. With fewer than ten benign training values, calibration is not considered stable enough and the configured fallback threshold is used.

How post-training adaptation works: recency-weighted EWMA

After training—or immediately when training is zero—the mean and variance use exponentially weighted updates. Recent behavior matters more than old behavior:

delta = y − mean_old
mean_new = mean_old + alpha × delta
variance_new = (1 − alpha) × (variance_old + alpha × delta²)

Ordinary drift

alpha = drift_alpha = 0.05 by default. Five percent of the current residual moves the mean into the new observation's direction.

Strong anomaly

alpha = suspicious_alpha = 0.005 by default. Only 0.5 percent of the residual moves the mean, ten times less than ordinary drift.

Numeric example: suppose the transformed mean is 2.4 and the current transformed value is 3.9, so delta = 1.5. Ordinary adaptation gives 2.4 + 0.05 × 1.5 = 2.475. Strong-anomaly adaptation gives 2.4 + 0.005 × 1.5 = 2.4075. The anomalous value is not ignored, but it moves the suspicious baseline only 0.0075 instead of 0.075.

What else changes after every observation?

Special case: TLS per-server byte models

TLS also maintains a byte-volume model for each known server. Before SSL training completes, matching byte values use Welford fitting. During detection, a TLS flow with no reasons uses ssl_baseline_alpha; a flow with at most ssl_max_small_anomalies reasons uses drift_alpha; a flow with more reasons uses suspicious_alpha. This per-flow byte update is separate from the source-IP/SSL/window adaptation described above.

Why adapt anomalous traffic at all? Freezing forever after an alert would make a legitimate permanent change alert forever. Learning every alert quickly would let repeated attacks poison the baseline. The design takes the middle path: always remain adaptive, use robust median/MAD to tolerate isolated outliers, and slow the mean/variance update when the aggregate evidence is strong.

The current observation is always scored against the model that existed before that observation. Alert emission comes first; adaptation happens afterward.

9. From feature reasons to a global IP anomaly

Terminology: the JSON event is called protocol_anomaly, but it is not one anomaly for DNS or HTTP across the network. It means one anomaly for one exact (source IP, protocol, window_start) group. The clearer name used below is source-IP/protocol/window anomaly.

1. Compute one source-IP/protocol/window anomaly

Consider the source-IP/protocol window identified by (10.0.0.5, dns, 12:00). Every DNS feature has its own model. That model calculates a z-score for the current feature value. Values whose z-scores remain below their thresholds add nothing. If the current flow_count value produces z=4.2 and the current dga_ratio value produces z=3.8, and both cross their thresholds, the detector creates one DNS anomaly:

source_protocol_window_score = 4.2 + 3.8 = 8.0
source_protocol_window_contribution = min(8.0, 10.0) / 10.0 = 0.80

The default contribution cap is protocol_score_cap = 10. A raw score of 4 contributes 0.4; a score of 8 contributes 0.8; every score of 10 or more contributes 1.0. This prevents one component containing many extreme features from contributing more than the complete global-score range.

2. Compute one destination-IP/window anomaly independently

The destination-IP window identified by (192.0.2.20, 12:00) has a different list of features and different feature histories. Suppose new_sources has z=3.7 and unique_ports has z=4.3, with both crossing their thresholds:

destination_window_score = 3.7 + 4.3 = 8.0
destination_window_contribution = min(8.0, 10.0) / 10.0 = 0.80

The calculation is numerically the same, but the input features and model key are different. The destination event becomes one component named target:192.0.2.20 inside the ensemble.

3. Group components by the exact same IP and window

global grouping key = (IP, window_start)

source-IP/protocol/window anomaly → IP = its source IP
destination-IP/window anomaly → IP = its destination IP
This is the relationship: source-side and destination-side anomalies are not joined merely because they describe the same connection. For a flow 10.0.0.5 → 192.0.2.20, the source/DNS anomaly votes in group (10.0.0.5, 12:00), while the destination anomaly votes in group (192.0.2.20, 12:00). They therefore form two different possible global-IP events. A destination component combines with source-protocol components only when their IP value and window start are identical—for example, when IP 10.0.0.5 has source-side anomalies and also receives anomalous traffic during the same window.

4. Combine all components in one group

Inside one (IP, window) group, DNS, HTTP, connection, SSH, and the destination component are separate votes. The first component contributes its normalized score. Each additional component adds the configured corroboration bonus, capped globally. Exact responsible UIDs present in at least two components add another capped bonus. Shared FUIDs are reported but do not add score.

vote_sum = Σ normalized component contributions
component_bonus = min(corroboration_bonus_cap, (component_count − 1) × corroboration_bonus)
UID_bonus = min(uid_bonus_cap, shared_UID_count × uid_bonus)
global_score = min(1, vote_sum + component_bonus + UID_bonus)

With the defaults, corroboration_bonus = 0.15, its cap is 0.30, each shared UID adds 0.10, and the UID-bonus cap is 0.20.

5. Decide whether to emit the global anomaly

effective_global_threshold = min(1, global_threshold / sensitivity)
effective_minimum_components = max(1, ceil(minimum_protocols / sensitivity))

emit if global_score ≥ effective_global_threshold
OR if component_count ≥ effective_minimum_components

The configuration name minimum_protocols is historical: the implementation counts independent components, and the destination component is included in that count. With default sensitivity 1, the score threshold is 0.65 and the component-count gate is 2.

Complete example for one IP and window: a DNS anomaly with raw score 4 contributes 0.40. An HTTP anomaly with raw score 3 contributes 0.30. Their vote sum is 0.70. Because two components exist, the corroboration bonus is 0.15, producing 0.85. If they share one responsible UID, another 0.10 produces global_score = 0.95. The global event stores both component anomalies and their feature-level reasons.

10. Why did the detector alert?

The detector stores reasons and responsible records rather than returning only a score. Attribution is feature-aware:

Reason typeHow responsible flows are selected
New peer or categorical valueRecords containing the first-seen peer or value.
Failure ratioRecords that satisfy the protocol's failure rule.
Port fan-outFlows to the destination with the largest set of ports.
DGA-like or no-answer ratioDNS records carrying the corresponding derived flag.

Each anomaly reports the feature value, learned mean, z-score, effective threshold, direction, explanation, responsible flow count, representative flows, and responsible UID/FUID sets.

11. Full example: a sudden DNS burst

Historical behavior

One workstation produced these DNS counts in seven active five-minute windows:

8, 9, 10, 10, 11, 12, 10

After ln(1+x), the historical median is approximately 2.398. MAD is approximately 0.087, so robust standard deviation is 1.4826 × 0.087 ≈ 0.129.

Current behavior

The workstation now produces 50 DNS records. Its transformed value is:

ln(1 + 50) ≈ 3.932

The robust z-score is approximately |3.932 − 2.398| / 0.129 = 11.89. This crosses a threshold of 3.5 and becomes a flow_count reason.

The same window may also show new peers, higher query entropy, more DGA-like queries, or more failures. Each crossing adds a separate reason and z-score. If HTTP or connection behavior is also anomalous for that IP, the global ensemble combines the independent evidence.

Optional detectors and operating modes

The adaptive statistical detector explained above is always the core detector. The following independent detectors run after it. They read the same converted window features, but they never modify the core model or its decisions.

Off

The module is not executed. Its score and contribution are zero.

Shadow

The detector runs and displays candidates for comparison. Its candidates are not official anomalies.

Active

The detector may add a module-only candidate to official anomalies. It can never remove, lower, or replace a core anomaly.

official anomalies = core anomalies ∪ candidates from Active optional detectors
Therefore: every core anomaly remains official in every mode.

If an Active detector and the core select the same IP@window-start, the optional finding is attached as extra evidence. If only the Active detector selects it, a new official anomaly is added. A module error is isolated: that module reports an error and the core result remains available.

Same-run comparison

Final global decisions are identified as IP@window-start. The IP may have entered the group through a source-IP/protocol/window anomaly, a destination-IP/window anomaly, or both. The Pipeline comparison tab compares the core set with a module's candidate set:

overlap = core IDs ∩ module IDs
core only = core IDs − module IDs
module only = module IDs − core IDs
decision agreement = |overlap| / |core IDs ∪ module IDs|
score difference = mean(|core score − module score|) over overlapping IDs

The core is a stable reference, not ground truth. A module-only result is a disagreement to investigate, not automatically a false positive; a core-only result is not automatically a module failure. The initial core_mirror_v1 module copies the core output and should therefore produce 100% agreement and zero score difference. This known answer validates the comparison path before a different model is introduced.

Dashboard: change each real detector independently between Off, Shadow, and Active. Every change recomputes the run from the selected capture, which makes method comparisons reproducible.

Additional detection methods

These methods are explained after the core statistical method because they are optional alternatives. Except for the graph detector, they run independently on each source-IP/protocol stream and on each destination-IP stream. A source stream uses its protocol-specific converted features; a destination stream uses destination features such as source count, protocol count, connection count, bytes, ports, and failures.

Robust multivariate relationships

This detector asks whether the combination of current values is unusual. Example: DNS query count and response count may each be ordinary alone, but their combination can be strange if they normally rise together and suddenly disagree.

1. Transform each feature j:
yⱼ = ln(1 + max(0, xⱼ))

2. Robustly standardize it from historical windows:
mⱼ = median(yⱼ history)
sⱼ = max(0.05, 1.4826 × median(|yⱼ − mⱼ|))
uⱼ = (yⱼ − mⱼ) / sⱼ

3. Learn covariance C from the historical standardized vectors.

4. Regularize unstable correlations with shrinkage λ:
C*ⱼₖ = (1 − λ) × Cⱼₖ, when j ≠ k
C*ⱼⱼ = max(Cⱼⱼ, 0.05) + 0.05

5. Measure joint distance from the historical standardized mean ū:
δ = u_current − ū
D² = δᵀ (C*)⁻¹ δ
multivariate_score = √(D² / p)

6. Candidate decision:
multivariate_score ≥ multivariate_threshold

The score is a distance, not a probability. Covariance describes which features normally move together. Shrinkage weakens unreliable learned relationships when history is short.

PCA reconstruction

PCA learns the dominant ways in which the historical feature values change together. It projects the current window onto those learned patterns and rebuilds it. The part that cannot be rebuilt is the reconstruction residual.

standardized current vector = u
reconstructed vector = projection of u onto the retained PCA components
PCA error = √(Σ(uⱼ − reconstructedⱼ)² / number_of_features)
candidate when PCA error ≥ pca_threshold

This adds detection of a new relationship pattern even when no single value is extremely large. The dashboard reports the features with the largest reconstruction residuals.

Isolation Forest

Each tree repeatedly chooses a feature and a random split. A window far from historical windows is separated in fewer splits. Many random trees are averaged so one lucky split does not decide the result.

mean_path = average number of splits needed to isolate the current window
isolation_score = 2^(−mean_path / expected_path_for_history_size)
candidate when isolation_score ≥ isolation_threshold

A score nearer 1 means easier to isolate and therefore more unusual. This method can find irregular regions that do not have an elliptical statistical shape.

Empirical rarity and novelty

For each feature, this detector counts how few historical values are at least as extreme as the current value. It does not assume a normal distribution.

tail_probability = min(1, 2 × (1 + smaller_tail_count) / (history_count + 1))
rarity_score = −log₁₀(tail_probability)
window score = largest feature rarity score
candidate when window score ≥ rarity_threshold

For example, score 1 means an estimated tail probability of 0.1; score 2 means 0.01. The added 1 prevents a false probability of zero with finite history.

Time-series level change

A point detector asks whether one window is unusual. This detector asks whether several recent windows have moved together to a new level. For every feature it compares the median of the recent windows with the median of the earlier reference windows.

scale = max(0.05, 1.4826 × median(|earlier value − earlier median|))
change_score = |recent median − earlier median| / scale
window score = largest feature change score
candidate when window score ≥ change_threshold

Using several recent windows makes a persistent change more important than a one-window spike.

Communication graph behavior

For each source IP and time window, all protocols are combined into one set of contacted destination IPs. Earlier sets form the source's communication graph history.

new_destination_ratio = new destinations / max(1, current destinations)
fanout_change = max(0, (current destination count − historical median) / historical robust scale)
graph_score = 0.6 × new_destination_ratio + 0.4 × min(1, fanout_change / 3)
candidate when graph_score ≥ graph_threshold

This adds direct detection of new relationships and sudden scanning-like fan-out. The explanation includes the new destination IPs.

History and adaptation for all optional methods

Known-normal folders and windows inside the capture-wide training interval enter history without producing candidates. Without training, the first minimum_points observations seed each stream; the next observation is the earliest that can be scored. Each method scores a current window before adding it to its rolling history. The history limit removes the oldest windows, so persistent new behavior gradually becomes the recent reference. Active and Shadow learn identically; only their effect on official output differs.
